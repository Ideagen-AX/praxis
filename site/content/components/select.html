Three select implementations, all filter-scoped. .filter-select, .cf-select and .filter-type-select live in praxis-filters.css. Tier 2 on ROADMAP.md.

Praxis has a real answer for one kind of picklist — .pillset/.pill in Fields, described there as "picklists as real radios", which is correct for three or four options. Above that it stops working and there is nothing to fall back to.

Record forms in this domain routinely pick from long, hierarchical, sometimes thousands-long lists: a site, an asset, a hazard category, a regulation clause. That is a combobox with typeahead, not a select.

Anatomy

  1. Trigger — a field showing the current value.
  2. Panel — a .px-pop surface holding the list.
  3. Filter input — inside the panel for the combobox form. .cn-find is the existing precedent for a leading-glyph search inside a menu.
  4. Option — with optional description and group heading.
  5. Selected tokens — for multi-select. .chip-area is reserved in praxis-rfield.css for something like this.

Variants

VariantUseAPG pattern
Native <select>Under ~15 fixed options. Genuinely the right answer more often than design systems admit — it is accessible, it works on touch, and it costs nothing—
ListboxStyled options, groups, descriptions, no typingListbox
ComboboxTypeahead over a long listCombobox
Multi-selectSeveral values, shown as removable tokensCombobox with aria-multiselectable

Open decision, and it is the whole design: whether Praxis ships one component with modes or three. Three is more honest — a native select and a typeahead combobox share a look and nothing else — but it means three names for what a form author thinks of as one thing.

States

  • Closed / open / filled / empty / disabled / invalid.
  • Loading — a remote option list. Depends on loading states.
  • No matches — empty state, inline form.
  • Too many to show — the state long lists actually hit. "Showing 50 of 1,284 — keep typing" is more useful than a truncated list with no explanation.

Responsive behavior

Desktop: panel anchored to the trigger. Phone: defer to the native control for the plain forms; the combobox becomes a full-height sheet, because a typeahead panel over a phone keyboard has about 200px to work with.

Code

praxis-controls.css for the trigger and panel; a script for the combobox. The panel should follow .px-pop exactly, for the same reason .tb-dropdown does — a list opened from a field and one opened from a toolbar should be the same object.

Usage guidelines

Do

  • Use a native <select> when it will do. It is the most accessible option and needs no script.
  • Use .pillset for three or four options — it shows them all without a click.
  • Say how many results a filter left.

Don't

  • Use a combobox for a yes/no. That is a radio or a switch.
  • Truncate a long list silently.
  • Move focus into the option list.

Accessibility

  • APG Combobox is the specification; follow it rather than improvising.
  • aria-activedescendant, not focus movement.
  • Result counts in a live region.
  • A native select is a legitimate accessible answer and should not be replaced for looks.
  • Fields carry no border in Praxis, so the fill is the whole affordance — --px-field against --px-surface must clear 3:1 as a control boundary under 1.4.11.
