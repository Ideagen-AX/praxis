The only loading affordance in Praxis is .mazlan-typing — the AI drawer's three dots, tied to that surface. No skeleton, no spinner, no inline loading. Tier 1 on ROADMAP.md.

Every one of the six design systems surveyed for the roadmap ships at least two of these, and Praxis pages fetch data: a search result set, a record, a filter's option list, an attachment upload. Today each of those either appears instantly or appears blank, and blank is indistinguishable from broken.

Three components, one page, because choosing between them is the actual design decision and splitting them across three pages hides it.

Anatomy

Skeleton

  1. Block — a muted shape matching the size of the content that will replace it.
  2. Shimmer — optional animation. Open question below.

Spinner

  1. Track and arc — a rotating partial ring. One size for inline use, one for a region.

Inline loading

  1. Spinner plus label — "Saving…", then a resolved state. Carbon's InlineLoading is the model: it resolves to a tick rather than vanishing, so the outcome is visible.

Variants

UseReach forWhy
A region whose shape is known — a table, a card grid, a record formSkeletonIt preserves layout, so nothing jumps when the data lands
A region whose shape is unknownSpinnerA skeleton that guesses wrong is worse than no skeleton
A control the user just pressedInline loadingThe feedback belongs on the thing they touched
Under 200msNothingA flash of skeleton reads as a glitch. This threshold should be a token, not folklore

Open decision: shimmer or no shimmer. A moving gradient is the convention and it is also the thing most likely to be wrong here — Praxis honours prefers-reduced-motion in seven places, and a shimmering table under a user who asked for less motion is a straightforward failure. If shimmer is taken, the reduced-motion fallback is a static fill, not a slower shimmer.

States

  • Idle — not rendered.
  • Pending — skeleton or spinner shown, container aria-busy="true".
  • Resolved — for inline loading only, a brief success state before it clears. This is what makes it worth having over a bare spinner.
  • Failed — not this component. An error empty state or a banner.

Responsive behavior

None of its own. A skeleton takes the shape of whatever it stands in for, so it inherits that component's responsive behaviour — which is an argument for skeletons being composed from a primitive block rather than shipped per-component.

Usage guidelines

Do

  • Match the skeleton to the real layout, so nothing moves when data arrives.
  • Put inline loading on the control the user pressed.
  • Wait ~200ms before showing anything.
  • Keep the resolved state visible for a moment. A save that silently stops looking busy has not told anyone it worked.

Don't

  • Skeleton a region whose shape you cannot predict — use a spinner.
  • Replace a whole page with skeletons when only one card is loading.
  • Animate under prefers-reduced-motion.
  • Use a spinner for something that takes more than a few seconds. That needs progress, and progress is a different component.

Accessibility

  • aria-busy on the container is what tells assistive technology the region is in flux; without it a skeleton is a set of meaningless empty boxes in the accessibility tree.
  • A standalone spinner needs role="status" and a label, or it is invisible to a screen reader — which is the same as no loading indicator at all.
  • prefers-reduced-motion: shimmer becomes a static fill, spin becomes a static or stepped indicator. Praxis already handles this correctly in seven places and there is no excuse for the eighth being the exception.
  • Do not move focus when content replaces a skeleton. The user has not asked to go anywhere.
  • Forced colors: a skeleton is a fill with no border and no text, so in forced-colors it disappears entirely. Needs an outline in that mode.
