.btn has no base rule anywhere in src/. .btn--primary styles a fill with no box, so a .btn renders as coloured text. Tier 1 on ROADMAP.md, and already the headline entry on what Praxis does not define.

This is the one gap that costs an hour every time someone meets it, because the failure is silent and looks like a Praxis bug rather than a missing definition. The buttons page documents the current state exactly: .tbtn and .admin-ghostbtn are complete, four classes get a fill only, five get a press transform and no box at all. praxis-filters.css says outright that its variants sit "on top of the host's .btn set" — a host that does not exist.

So this page is not really about designing a button. .tbtn already is the Praxis button, at 40px with a tool shadow. The question is what .btn should be given that.

Anatomy

  1. Box — height, inline padding, radius, the thing that is missing.
  2. Label — 14px/600 in every existing Praxis button.
  3. Leading glyph — optional, 18–20px, gap:7px in .tbtn.
  4. Trailing glyph — for a split or menu button.

Variants

The decision this page exists to force. Three options, and they are not equivalent:

OptionWhat .btn becomesCost
Alias.btn is a second name for .tbtn — same 40px, same tool shadowCheapest, and honest about the fact that Praxis has one button. But .btn--primary and .tbtn--primary already both exist with the same treatment, so the alias makes the duplication permanent
Smaller sibling.btn is the 32px form-and-dialog button; .tbtn stays the 40px toolbar buttonMatches how .iconbtn (34px) and .tbtn--icon (40px) already coexist, and that precedent is documented as deliberate. Two names, two real sizes
Base plus size modifiers.btn is the box; .btn--sm/--md/--lg set height; .tbtn becomes an alias of .btn--lgThe conventional answer and the most work. It also means touching .tbtn, which is load-bearing in six sheets

Recommendation: the smaller sibling. It is the only one of the three that adds something the system does not have — a button that fits inside a card or a dialog footer without the 40px toolbar presence — and it does not touch .tbtn.

Tone variants, whichever option wins: --primary (exists as a fill), --danger (missing entirely and needed by the confirm dialog), --ghost (exists on .tbtn).

States

All of these already exist and are already correct — they are applied to .btn in praxis-core.css today, over nothing. Defining the base is what makes them visible.

  • Hover — shadow lift via --px-tool-shadow-hover.
  • Press — scale(.97), from the global press-feedback pass in praxis-core.css.
  • Focus-visible — 2px --praxis-color-border-focus.
  • Disabled — opacity:.45, cursor:not-allowed, no shadow, matching .iconbtn.
  • Loading — does not exist. Depends on the loading component.

Responsive behavior

None of its own. Buttons inherit the phone gutter through their container, and --praxis-control-h (32px) already exists as the "compact action control height" token — which is a strong hint that the smaller sibling above was always the intent.

Code

Belongs in praxis-core.css, not praxis-admin.css. .tbtn lives in the admin sheet for historical reasons and that sheet is the largest in the system; .btn is foundational and every page loads core.

Markup contract

ItemRequirement
Element<button type="button">. Praxis's press-feedback rules key on button, [role="button"], so a styled <div> gets the visual and none of the keyboard behaviour
typeAlways explicit. An unset type inside a form is submit, which is the single most common cause of a Cancel button submitting
Icon.material-symbols-rounded span, converted by praxis-lucide.js. Sized by the button rule, not the span
Icon-onlyNot this component. Use .iconbtn (34px) or .tbtn--icon (40px), and give it an aria-label
DisabledThe disabled attribute, or aria-disabled="true" where the control must stay focusable to explain why
JSNone. This is CSS only

Token reference

Every value needed already exists, which is the clearest possible sign this should have been defined long ago.

TokenUse
--praxis-control-h32px — the "compact action control height", already in the token file and used by almost nothing
--px-tool / --px-tool-shadowNeutral fill and rest shadow
--px-tool-shadow-hoverHover
--px-primary-grad / --px-primary-fg / --px-primary-shadowThe primary variant, already audited to 5.00:1
--praxis-radius-sm8px. Note .tbtn uses a hard-coded 10px, which is off the 8/12/16 scale — worth correcting rather than copying
--praxis-color-border-focusFocus ring

Missing: a danger fill. There is --praxis-color-status-danger for an ink and --praxis-tone-danger-* for a chip, but no gradient equivalent of --px-primary-grad, and a red button built from the status ink would fail contrast the same way the teal one did before it was fixed.

Usage guidelines

Do

  • Use .tbtn in a toolbar band and .btn everywhere else, if the smaller-sibling option is taken.
  • Label with a verb naming the outcome.
  • Keep one primary per view.

Don't

  • Use .btn until it has a base — today it renders as coloured text and that is not a bug you should work around locally.
  • Reach for .pill-btn, .lg-btn, .qa or .sortbtn expecting a button. All four are fill-or-hover-only. See Buttons.

Accessibility

  • Real <button>, so Enter and Space work and the control is in the tab order without help.
  • Focus indicator is never removed — the fill alone does not indicate focus, a point Form controls already makes about checkboxes.
  • Contrast: the primary fill was measured at 5.00:1 at the top of the gradient after a documented failure at 3.86:1. Any new fill variant must be measured the same way, across the whole gradient rather than at one stop.
  • Forced colors: a button whose only boundary is a shadow disappears. This component is the strongest argument for ROADMAP.md F2.
