.pager has no base rule. praxis-core.css styles .pager__btn on hover, on disabled-hover and in the press-feedback pass — three rules refining a button that is never defined. Tier 1 on ROADMAP.md.

This is one of the six name-only families the roadmap audit turned up beyond the ones gaps.html already lists, and it is the one that matters most: every search result, every audit register, every findings list needs paging, and there is nothing to build it from.

Anatomy

  1. Range readout — "1–25 of 1,284". The most useful part and the one most often left out.
  2. Previous / next — .pager__btn, disabled at the ends.
  3. Page numbers — optional, with truncation. See Variants.
  4. Rows per page — a select. Belongs here rather than in the toolbar, because it changes what paging means.

Variants

VariantUseNote
SimplePrevious / next plus the range readoutCorrect default for a server-paged table where the total is expensive to know
NumberedAdds page numbers with an ellipsisOnly worth it when a user might jump. Needs a truncation rule: how many either side of current, and whether first and last are always shown
Load moreA single button appending the next pageWrong for this domain. An auditor needs to cite "row 340 of 1,284"; an append-only list has no addressable position

Open decision: whether infinite scroll is permitted at all. The recommendation is no, for the reason above — regulated work needs stable, quotable positions, and an infinite list cannot be printed either (see ROADMAP.md F1).

States

  • First page — previous disabled.
  • Last page — next disabled. Requires knowing the total; the simple variant may not.
  • Single page — the whole component hides. Undecided whether the range readout stays, and it probably should: "25 of 25" is information.
  • Loading — the range readout is the natural place for it. Depends on the loading component.
  • Current page — .pager__btn--active, which praxis-core.css already excludes from the hover treatment, so the name is effectively reserved.

Code

Belongs in praxis-core.css beside the hover rules that already reference it. CSS only — paging is the application's data concern, and a Praxis script that owned page state would be reaching past where the system stops.

Usage guidelines

Do

  • Show the range readout. It is the difference between paging and guessing.
  • Put rows-per-page in the pager, not the toolbar.
  • Keep the control in the same place on every list.

Don't

  • Use infinite scroll for a register an auditor might cite.
  • Hide the pager when there is one page — say so instead.
  • Reset to page 1 silently when a filter changes. Say that too.

Accessibility

  • aria-current="page" is what conveys position; the class is decoration.
  • Icon-only previous and next need labels.
  • After a page change, focus should not be lost. Moving it to the top of the table, or announcing the new range in a live region, are the two workable answers; doing neither leaves a keyboard user at the bottom of a page that just replaced itself.
  • Targets: 32px is below the 44px WCAG 2.5.8 minimum. Acceptable at desktop under the spacing exception, which is precisely why the phone variant drops the numbers.
