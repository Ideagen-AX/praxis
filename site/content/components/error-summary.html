Nothing aggregates form errors. .form-alert exists in praxis-rfield.css as a single inline message and .req marks a required field. There is no summary. Tier 1 on ROADMAP.md.

This is the one item on the Tier 1 list taken directly from GOV.UK, where it is the centrepiece of their accessibility work rather than a nicety. The reasoning is simple: on a long form, a user who submits and gets inline errors twelve fields down has no way to know how many there are, where they are, or whether they have fixed them all.

Praxis's record forms are long by nature — an incident report or an audit checklist runs to several .section blocks of .rfield rows, and sections can be collapsed, which means an error can be inside something that is closed. That last part makes this more than a convenience: without a summary, a validation error can be genuinely invisible.

Anatomy

  1. Container — a danger-toned box at the top of the form.
  2. Heading — "There is a problem" is GOV.UK's wording and it is hard to improve on: it is plain, it is not blaming, and it is the same every time.
  3. List — one link per error, in the order the fields appear in the DOM, not in the order validation ran.
  4. Link — text is the error message; the target is the field.

Variants

One. A form either has errors or it does not.

Open decision: whether it also covers the section-level case. A record page can have errors spread across four collapsed sections, and a flat list of twelve links loses that structure. Grouping by section — "Immediate actions (3)" — is more useful and more work, and it needs the summary to know about .section, which couples two components.

States

  • Absent — not rendered at all. Not hidden: an empty summary in the DOM is something a screen reader can land on.
  • Present — rendered and focused. Focus, not just scroll — see Accessibility.
  • Updated — a second submit with fewer errors replaces the list and re-focuses. The re-focus is what tells a user their fix worked.

Responsive behavior

ViewportBehaviour
AllFull width of the form column, above the first field, inside the scroll container
PhoneUnchanged. This is the viewport where it matters most, because less of the form is visible at once

One real constraint: Praxis's shell puts the form inside .admin-body or .page-body, which is the scroll container, not the window. A summary that scrolls its target into view has to scroll that element. This is the same trap the reference site's table of contents hit.

Code

praxis-rfield.css, beside .form-alert — that sheet already owns the record form's validation vocabulary.

It needs a script, and this is the one place a Praxis script should own behaviour rather than paint: moving focus, and scrolling the right container, are both easy to get wrong and both invisible when wrong.

role="alert"On the container, so it is announced when it appears. Only correct because it is rendered on submit rather than present at load
tabindex="-1"So it can receive programmatic focus

aria-describedbyFrom the input to its inline message

Usage guidelines

Do

  • Render it on submit, not on blur. A summary that appears while a user is still typing is noise.
  • List errors in DOM order.
  • Write the message as an instruction: "Enter the immediate cause", not "This field is required".
  • Keep the inline message too. The summary is navigation; the inline message is context.

Don't

  • Leave an empty summary in the DOM.
  • Use it for warnings or for anything the user can ignore.
  • Count errors in the heading. "There is a problem" is stable; "There are 3 problems" changes on every submit and gives a screen-reader user a number they did not ask for before the list they did.

Accessibility

  • Focus the summary on render. Scrolling to it is not enough — a screen reader user is wherever their cursor was, which is the submit button at the bottom.
  • Expand collapsed ancestors before focusing a target. The single most likely bug in this component.
  • aria-invalid and aria-describedby on every failing field, or the summary is the only place the error exists.
  • Scroll the right container — .admin-body, not the window.
  • Colour is not the only indicator: the inline message is text and the field gets aria-invalid, so a red border is reinforcement rather than the signal.
