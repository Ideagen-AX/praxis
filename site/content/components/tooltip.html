Nothing is defined in src/ for this. Not a class, not a rule, not a script — a grep for tooltip across every sheet returns zero. This page is the brief for what it should be, not documentation of what it is. Tier 1 on ROADMAP.md.

Praxis leans on icon-only controls harder than most systems: .iconbtn (34px), .tbtn--icon (40px), .appbar__iconbtn (40px) and every button in the nav rail. Four separate sizes of unlabelled square, and no component to label any of them.

Today the only thing holding that together is the native title attribute, which the app shell and this reference site both use. That is not a substitute: it does not appear on keyboard focus, it cannot be styled, its delay is fixed by the browser, and on touch it does not appear at all.

Anatomy

  1. Trigger — the control being labelled. Not part of the component; the tooltip attaches to whatever is already there.
  2. Bubble — the floating label. Single line in the common case, wrapping at a max-width for the rest.
  3. Tail — optional. Open question below.

Three parts, and the third is the only real decision. Everything else about this component is positioning, timing and accessibility wiring.

Variants

One. A tooltip that carries anything more than a short label is a popover, and Praxis already has that surface in .px-pop.

The naming question, which is worth settling before any CSS is written. Praxis prefixes shared chrome primitives with px- — .px-pop, .px-skip, .px-menu, .px-navdrawer, .px-navtoggle. A tooltip is chrome, so .px-tip follows the convention. But there is a case for making it .px-pop--tip instead, so a menu, a flyout and a tooltip are visibly one surface with three densities. That would be consistent with how praxis-controls.css already reasons about .tb-dropdown ("surface follows .px-pop exactly, so a menu opened from the toolbar and one opened from the nav rail are the same object"). The counter-argument is that a tooltip is not interactive and a popover is, and merging them invites putting a link in a tooltip.

States

Hidden, shown, and shown-from-keyboard. The third is the one the title attribute gets wrong and the reason this component has to exist.

  • Hover — appears after a delay, disappears immediately. The delay is what stops a tooltip firing on every control the pointer crosses on the way somewhere.
  • Focus-visible — appears with no delay. A keyboard user has already committed to the control.
  • Escape — dismisses without moving focus. Required by WCAG 1.4.13.

Code

Nothing to link yet. When it lands it belongs in praxis-controls.css — that sheet exists for exactly this class of thing, "the small shared controls that are not the toolbar band", and every page that needs a tooltip can afford four more kilobytes.

It will need a script. Positioning that survives a scroll container, a viewport edge and a resize:horizontal frame is not expressible in CSS alone, and Praxis has no positioning library. The proposed markup:

Markup contract

Praxis ships no framework bindings, so there are no props and no events — the contract is the markup and the attributes.

ItemRequirement
data-px-tipOn the trigger. Its value is the label. Undecided: whether this is the only entry point, or whether an existing title is adopted automatically — auto-adoption would upgrade every icon button in the app shell with no markup change, at the cost of being surprising
aria-labelStill required on the trigger, independently. A tooltip is a visual affordance; the accessible name must not depend on it
aria-describedbySet by the script, pointing at the bubble
role="tooltip"On the bubble
JS APISelf-wiring on DOMContentLoaded with a MutationObserver, matching how praxis-lucide.js and the five chrome scripts already behave. No init call

Token reference

Nothing new should be needed. The bubble is a floating chrome surface and Praxis already has the material for one:

TokenUse
--px-overlayThe shadow. Same as .px-pop and .tb-dropdown
--px-surfaceFill, under the Praxis variant
--praxis-radius-sm8px. A tooltip should be the tighter radius, not the 12px of a menu
--praxis-type-size-sm13px
--praxis-motion-fast120ms for the fade

One value is genuinely missing: the hover delay. Nothing in the token file expresses "wait before showing", and it is a shared decision, not a per-call one. Candidate: --praxis-motion-tip-delay.

Praxis has no Figma library, so there is nothing to adapt from or to. Recorded here because the section exists on every component page and the honest answer is "not mapped" rather than silence.

Usage guidelines

Do

  • Use it to name an icon-only control.
  • Keep it to a few words. If it needs a sentence, the control needs a visible label.
  • Set aria-label as well, always.

Don't

  • Put a link, a button or anything focusable inside it — that is .px-pop.
  • Use it to hold information a user needs to complete a task. On touch they will never see it.
  • Use it on a control that already has a visible label.

Accessibility

  • WCAG 1.4.13 Content on Hover or Focus is the governing criterion: dismissable without moving the pointer, hoverable so the pointer can move onto it, and persistent until dismissed or the trigger loses focus. All three are easy to get wrong and the native title fails the first.
  • The bubble is role="tooltip" and referenced by aria-describedby — a description, not a name.
  • It must not be the only source of the accessible name.
  • Forced colors: the bubble's separation from the page comes entirely from --px-overlay, and shadows are dropped in forced-colors mode. It needs a border that only appears there. See ROADMAP.md F2 — this component is a concrete instance of that foundation gap rather than a special case.
